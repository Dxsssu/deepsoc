# 当前进度文档

## 1. 引入核心数据结构溯源任务树

### 1.1 核心定义

当前系统已经引入 `TTT（Traceback Task Tree，溯源任务树）` 作为事件处置过程中的核心数据结构。  
它的定位是整个多智能体系统的“共享黑板”，用于统一表达当前事件的溯源目标、任务拆解结果、执行进展和状态变化。

TTT 的基本组织方式为树形结构：

- 第一层节点：表示当前事件溯源中的核心方向或阶段性目标，例如“威胁情报查询”“资产信息查询”“告警上下文搜集”“失陷判定”等。
- 第二层节点：表示围绕某个方向拆解出来的具体执行任务，例如“查询源 IP 威胁情报”“查询目的 IP 资产信息”“检索登录成功日志”等。
- 更深层节点：按实际需要继续细分，用于表达更复杂的多步排查链路。当前设计不限制层级深度。

每个节点通常包含以下核心信息：

- `node_id`：节点唯一标识，用于在多轮迭代中稳定追踪同一个任务节点。
- `title`：节点名称，用于表达该节点对应的任务目标或操作内容。
- `status`：节点状态，当前主要包括 `todo`、`in_progress`、`done`、`n/a`。
- `children`：子节点列表，用于表达任务拆解关系。

其中：

- 非叶子节点更偏向“规划语义”，用于表达某个排查方向或阶段。
- 叶子节点更偏向“执行语义”，是后续由 `_manager` 选择、再下发给 `_operator` 的最小可执行任务单元。

通过引入 TTT，系统不再依赖一次性静态任务列表，而是能够以“结构化任务树”的方式持续维护事件处置全貌，为后续的任务派发、状态更新和多轮循环提供统一基础。

### 1.2 结构示例

下面给出一个简化的 TTT JSON 结构示例：

```json
{
  "schema_version": "1.0",
  "event_id": "event_demo_001",
  "round_id": 1,
  "root_nodes": [
    {
      "node_id": "1",
      "title": "威胁情报查询",
      "status": "todo",
      "children": [
        {
          "node_id": "1.1",
          "title": "查询源 IP 威胁情报",
          "status": "todo",
          "task_type": "query",
          "assignee": "_operator",
          "children": []
        }
      ]
    },
    {
      "node_id": "2",
      "title": "资产信息查询",
      "status": "todo",
      "children": [
        {
          "node_id": "2.1",
          "title": "查询目的 IP 资产信息",
          "status": "todo",
          "task_type": "query",
          "assignee": "_operator",
          "children": []
        }
      ]
    },
    {
      "node_id": "3",
      "title": "失陷判定",
      "status": "todo",
      "children": [
        {
          "node_id": "3.1",
          "title": "检索告警时间窗内是否存在登录成功记录",
          "status": "todo",
          "task_type": "query",
          "assignee": "_operator",
          "children": []
        }
      ]
    }
  ]
}
```

从这个结构可以看到：

- `root_nodes` 表示整棵任务树的顶层节点集合。
- 第一层节点负责表达排查方向。
- 第二层节点负责表达可实际执行的具体任务。
- 后续每轮执行后，系统会围绕这些节点持续更新 `status`，而不是重新生成一份全新的任务列表。

## 2. 任务派发

在当前多智能体协作流程中，任务派发已经围绕 TTT 形成了一条较为清晰的责任链。  
TTT 不只是任务列表，更是各角色协同的统一依据，所有角色都围绕同一棵任务树开展工作。

### 2.1 Captain 的功能

`_captain` 是系统中的总规划者，负责站在全局视角维护整棵 TTT。

其核心职责包括：

- 在事件首次进入系统时，结合告警内容、上下文和 SOP 参考，初始化一棵完整的 TTT。
- 在后续每一轮循环中，根据上一轮执行结果和专家总结，更新 TTT 中相关节点的状态。
- 始终维护最新版本的 TTT 快照，使其作为系统内统一的“全局参考”。

换句话说，Captain 关注的是“整棵树当前长什么样、哪些节点已完成、哪些节点仍待推进”，而不是直接负责执行具体操作。

### 2.2 Manager 的功能

`_manager` 是任务调度者，负责根据当前 TTT 的实际情况进行任务抽取和派发。

其核心职责包括：

- 从当前 TTT 中检索所有 `status=todo` 的叶子节点。
- 结合节点内容、当前事件上下文以及上一轮结果，选择一个最值得优先执行的节点。
- 将该节点转换为面向 `_operator` 的具体执行任务并完成下发。

这里有两个关键点：

- Manager 不是一次派发整棵树，而是每轮只选择一个待办节点推进。
- 选择逻辑不是固定写死顺序，而是结合当前 TTT 的实际状态动态决策。

因此，Manager 的定位更接近“调度中枢”，负责把 Captain 的全局规划转化为当前这一轮最值得执行的单个任务。

### 2.3 Operator 的功能

`_operator` 是执行者，负责承接 Manager 下发的任务并完成实际操作。

其核心职责包括：

- 接收 Manager 派发的当前节点任务。
- 结合可用工具能力，执行对应查询或操作。
- 将执行结果返回给系统后续环节。

Operator 关注的是“怎么把这个任务做出来”，因此它属于执行层而不是规划层。

### 2.4 Expert 的功能

`_expert` 是结果总结者，负责站在专业分析视角对执行结果进行归纳、解释和反馈。

其核心职责包括：

- 接收 Operator 的执行结果。
- 对结果进行总结，提炼有效证据、识别问题和不足。
- 将总结结果反馈给 Captain，作为下一轮更新 TTT 的依据。

因此，Expert 并不负责直接修改任务树，而是通过“总结结果”的方式，把信息回流给 Captain。

### 2.5 整体派发链路

综合来看，当前任务派发机制可以概括为如下闭环：

1. Captain 初始化或更新 TTT，并维护全局状态。
2. Manager 从 TTT 中选取一个 `todo` 节点。
3. Manager 将该节点下发给 Operator 执行。
4. Operator 执行任务并返回结果。
5. Expert 对执行结果进行总结，并反馈给 Captain。
6. Captain 根据总结更新 TTT 节点状态，并决定是否进入下一轮循环。

这一机制的意义在于：

- 规划与执行被清晰拆分；
- 所有任务都围绕统一的 TTT 展开；
- 每一轮只推进一个具体待办节点，便于逐步收敛；
- 通过 Expert 回流总结，Captain 可以持续更新全局判断，而不是依赖零散执行结果直接做决策。

## 3. SOP 知识库驱动的“冷启动”机制

为了减少新告警进入系统时“从零规划”的成本，当前系统已经开始引入基于 SOP 知识库的“冷启动”机制。

这里的核心思路是：

- 将现有 SOP（标准作业程序）知识进行结构化处理，而不是仅作为自然语言文档存放。
- 当接入一条新的安全告警时，系统先在 SOP 知识库中检索最相关的 SOP。
- 命中的 SOP 将作为 Captain 初始化 TTT 时的重要参考，直接参与构造首版任务树骨架。

### 3.1 SOP 知识的结构化处理

当前 SOP 知识库已经采用统一结构进行组织，每条 SOP 至少包含以下核心字段：

- `sop_name`：SOP 名称，用于标识该条标准流程。
- `sop_index`：与告警名称强相关的简短索引字段，用于向量相似度检索。
- `workflow_steps`：标准处置流程步骤列表，每一步仅保留：
  - `step_name`
  - `step_content`

这种设计的目的，是把原本偏文档化的 SOP 转换为“可被程序消费”的结构化知识，从而支持后续检索和映射。

### 3.2 新告警接入时的冷启动过程

当系统接入一条新的 event 时，不再完全依赖 Captain 从头规划，而是优先触发 SOP 检索。

当前的处理流程如下：

1. 系统读取 event 的关键信息，例如 `event_name`、`message`、`context`、`source`、`severity`。
2. 将这些信息组合为检索文本，与 SOP 知识库中的 `sop_index` 和流程内容进行向量相似度比对。
3. 选择最相关的一条或少量几条 SOP 作为候选参考。
4. 将命中的 SOP 内容注入给 Captain，作为初始化 TTT 时的输入上下文。

这样做的效果是：新告警进入系统时，Captain 不需要完全从空白状态开始拆解任务，而是可以优先参考已有的标准排查框架完成首版规划。

### 3.3 SOP 到 TTT 的映射方式

在当前设计中，命中的 SOP 不会直接原样替代 TTT，而是作为“初始化骨架”的参考来源。

具体来说：

- SOP 中的 `workflow_steps` 会被 Captain 读取并理解。
- Captain 会将这些标准步骤映射为 TTT 的初始节点结构。
- 必要时，Captain 可以根据当前事件上下文对步骤做适度调整，例如：
  - 合并不必要的步骤；
  - 将一个步骤拆解为多个更适合执行的子节点；
  - 保留 SOP 的主干逻辑，但针对当前告警补充更贴近现场的任务描述。

因此，SOP 的作用不是僵硬地“替代思考”，而是帮助系统快速生成一棵具备合理方向的初始任务树。

### 3.4 冷启动机制的价值

引入 SOP 知识库驱动的冷启动机制后，系统获得了几个明显收益：

- 新事件进入后的首轮规划更加稳定，不容易偏离标准排查路径。
- Captain 初始化 TTT 的速度更快，不需要完全依赖即时推理从零拆解。
- 系统的初始任务树更容易与真实安全运营经验对齐。
- 随着 SOP 库持续积累，系统在不同类型告警上的首轮响应质量会逐步提高。

整体来看，这一机制使得系统能够把“已有安全经验”前置到事件进入时刻，从而让 TTT 的初始化不再只是临场推理结果，而是建立在 SOP 知识基础上的结构化冷启动。

## 4. 溯源任务树更新机制（正在进行）

TTT 不只是一个静态规划结果，还需要具备基于环境反馈持续调整的能力。  
换句话说，系统在运行过程中不能假设所有节点都一定可执行，而是要允许任务树根据真实执行情况进行重规划。

当前这一部分机制仍在持续完善中，但已经实现了一条重要能力：  
当某个 TTT 节点在实际执行阶段无法推进时，系统可以对该节点进行“不可执行标记”，避免整条溯源链路被卡死。

### 4.1 当前已实现的更新能力

在实际执行过程中，如果某个 TTT 节点由于客观条件限制无法执行，例如：

- 当前网络环境中缺乏对应数据源；
- 没有合适的 MCP 工具可调用；
- 现有能力无法支撑该任务落地执行；

那么 `_operator` 不会继续强行执行，也不会伪造结果，而是会将该任务标记为 `fallback`。

随后：

1. `operator` 将无法执行的信息和失败上下文反馈出来；
2. `expert` 对该执行结果进行总结，明确说明该节点无法继续推进的原因；
3. `captain` 根据 expert 的反馈更新 TTT；
4. 对应节点会被直接标记为 `[N/A]`。

### 4.2 当前机制的意义

这一机制的价值在于，它让 TTT 具备了最基础的“基于反馈更新状态”的能力，而不是要求所有节点都必须成功完成。

如果没有这条机制，系统会出现一个明显问题：

- 某个节点由于工具或环境限制始终无法执行；
- 但任务树中该节点又一直保持 `todo`；
- Manager 会持续围绕它调度，整个溯源循环可能因此陷入阻塞或死锁。

通过引入 `fallback -> expert总结 -> captain标记 N/A` 的链路，系统可以明确承认“这个节点在当前条件下不可执行”，从而让任务树继续向其他可推进节点收敛，而不是被单点能力缺口拖住。

### 4.3 当前阶段定位

因此，从当前进度来看，TTT 更新机制已经具备了“基于执行失败进行状态调整”的基础能力。  
后续仍需要继续完善的，是更丰富的动态重规划能力，例如：

- 遇到执行失败后，是否自动生成替代节点；
- 节点状态变化后，如何影响后续节点优先级；
- 如何让整棵树在多轮反馈中逐步演化，而不仅仅是更新单个节点状态。

这也是当前溯源任务树更新机制仍被标记为“正在进行”的原因。

### 4.4 动态重规划能力（设计中）

在更理想的状态下，TTT 不仅要能更新节点状态，还要能根据执行反馈对整棵树进行动态重规划。  
这一部分逻辑相对复杂，目前仍在设计中，但已经可以明确几个关键方向。

第一个典型场景是：

- 某个节点执行失败后，系统是否不只是将其标记为 `N/A`，而是进一步自动生成一个“替代节点”。

例如：

- 原始节点要求“查询某类专有设备日志”；
- 但当前环境中没有对应设备，或者没有可调用的 MCP 工具；
- 此时系统未来可能不只是简单结束该节点，而是自动改写为其他替代路径，例如“通过网络流量侧日志进行旁路验证”或“改为查询边界设备审计日志”。

这意味着系统不再只是承认“做不了”，而是尝试在当前能力边界内寻找新的排查路径。

第二个典型场景是：

- 某个节点执行成功后，返回结果中出现了新的关键线索，系统是否需要据此更新后续节点，甚至新增新的调查方向。

例如：

- 原本节点只是查询登录失败日志；
- 但执行结果中发现同一源 IP 在相近时间内存在登录成功记录；
- 那么后续任务树就不应继续停留在“攻击尝试”视角，而应立即进入“失陷判定”甚至“主机排查”方向。

在这种情况下，TTT 的变化不只是某个节点从 `todo` 变成 `done`，而是整棵树的后续关注重点都可能发生变化。

总体来说，这类动态重规划能力会让 TTT 从“任务状态记录器”进一步演进为“可随证据变化而自适应调整的推理式规划结构”。  
但由于这里会涉及节点新增、节点替换、优先级重排、以及结构稳定性控制等多个问题，目前这一部分仍在设计中，尚未完全落地。

## 5. 讨论问题

### 5.1 SOP 知识库是否适合采用向量检索

当前知识库设计中，一个值得继续讨论的问题是：  
SOP 知识库是否真的适合采用与“历史案例库”相同的向量检索方式。

从历史案例库的角度来看，向量知识库的价值是比较明确的：

- 后续如果系统加入“以往研判思路”或“历史处置案例”，那么当前输入事件可以与历史案例做向量化相似度比对；
- 当相似度超过某个阈值时，就可以认为这是一个具有参考价值的相似案例；
- 系统可以进一步复用历史案例中的排查路径、关注重点或处置经验。

在这种场景下，向量知识库是天然适合的，因为历史案例本身就具有“经验参考”和“语义相似匹配”的特征。

但对于 SOP 知识库，情况可能并不完全一样。

SOP 的本质更接近“标准流程模板”，它通常是按照告警类型进行分类组织的。  
因此，当前一个直观思路是：

1. 先由 LLM 判断当前告警属于哪一类；
2. 再直接访问该类型对应的 SOP；
3. 将这份 SOP 作为初始化 TTT 的参考。

如果采用这种方式，那么 SOP 的访问逻辑更像“分类命中”而不是“语义检索”，向量检索能力似乎并没有被充分利用。

因此，这里存在一个需要继续讨论的设计问题：

- 历史案例库适合做向量检索；
- 但 SOP 知识库是否也应该做成同样的向量检索模式，当前仍不完全明确。

换句话说，SOP 知识库未来可能存在两种不同方向：

- 方向一：继续保留向量检索模式，让 event 与 SOP 做语义相似度匹配；
- 方向二：将 SOP 更明确地设计为“告警类型 -> 标准流程模板”的映射，由 LLM 或规则先完成类型识别，再直接命中对应 SOP。

这两种方向各有优劣，目前仍需要结合后续知识库扩展方式、告警分类稳定性，以及实际命中效果进一步讨论和验证。
